# AI Agent 消息外键约束问题

## 问题描述

AI Agent 成功触发并尝试发送消息，但保存消息到数据库时失败，错误信息：

```
插入或更新表 "messages" 违反外键约束 "messages_sender_id_fkey"
```

## 错误日志

```
Agent 弗洛洛 (762064a7-d918-44c7-bac9-8a33b1e4933a) sending message 035bbc0d-17cf-46bd-b126-c635c23b1e3f to group 9c4c9b42-8118-4f7b-8738-a08f408a5e86
Database operation failed: 插入或更新表 "messages" 违反外键约束 "messages_sender_id_fkey"
```

## 根本原因

**位置**：`server/migrations/20251201000001_create_messages_table.sql`

**问题**：
```sql
CREATE TABLE messages (
    id UUID PRIMARY KEY,
    sender_id UUID NOT NULL REFERENCES users(id),  -- ❌ 外键约束要求 sender_id 必须存在于 users 表
    -- ...
);
```

- `messages.sender_id` 有外键约束指向 `users.id`
- AI Agent 的 ID 存储在 `ai_agents` 表中，不在 `users` 表中
- 当 AI Agent 发送消息时，使用 AI Agent ID 作为 `sender_id`
- 数据库检查外键约束失败，因为 AI Agent ID 不在 `users` 表中

## 设计考虑

### 为什么 AI Agent 不应该是 User？

1. **不同的实体类型**：
   - User：真实用户，有登录凭证、个人信息、隐私设置等
   - AI Agent：虚拟助手，有性格配置、触发规则、统计数据等

2. **不同的生命周期**：
   - User：由用户注册创建，独立存在
   - AI Agent：由群组管理员创建，依附于群组

3. **不同的权限模型**：
   - User：可以创建群组、添加好友、修改个人信息
   - AI Agent：只能在所属群组中发送消息

4. **不同的数据模型**：
   - User：email、password_hash、avatar_url、bio 等
   - AI Agent：toxicity_level、enthusiasm_level、trigger_keywords 等

### 为什么需要多态 sender_id？

在消息系统中，`sender_id` 需要支持两种类型：
- **用户消息**：`sender_id` → `users.id`
- **AI 消息**：`sender_id` → `ai_agents.id`

PostgreSQL 不支持多态外键（一个字段指向多个表），因此我们有以下选择：

1. **移除外键约束**（✅ 推荐）
   - 优点：灵活，支持多态
   - 缺点：失去数据库级别的引用完整性
   - 解决：在应用层验证

2. **使用联合表**
   - 创建一个 `senders` 表，包含所有可能的发送者
   - 优点：保持外键约束
   - 缺点：复杂，需要额外的表和查询

3. **将 AI Agent 作为特殊用户**
   - 在 `users` 表中为每个 AI Agent 创建记录
   - 优点：保持外键约束
   - 缺点：混淆概念，AI Agent 不是用户

## 解决方案

**文件**：`server/migrations/20251206000001_allow_ai_agent_as_sender.sql`

### 方案：移除外键约束

```sql
-- Drop the existing foreign key constraint
ALTER TABLE messages DROP CONSTRAINT IF EXISTS messages_sender_id_fkey;

-- Drop the foreign key constraint on receiver_id as well for consistency
ALTER TABLE messages DROP CONSTRAINT IF EXISTS messages_receiver_id_fkey;

-- Update comments to reflect the new behavior
COMMENT ON COLUMN messages.sender_id IS 'UUID of the message sender. Can be either a user ID (users.id) or an AI Agent ID (ai_agents.id). Check is_ai_generated to determine the type.';
COMMENT ON COLUMN messages.is_ai_generated IS 'TRUE if message was generated by an AI Agent. In this case, sender_id refers to ai_agents.id instead of users.id';

-- Add index for AI-generated messages
CREATE INDEX IF NOT EXISTS idx_messages_ai_generated 
    ON messages(is_ai_generated, group_id, timestamp DESC) 
    WHERE is_ai_generated = TRUE;
```

### 应用层验证

虽然移除了数据库级别的外键约束，但我们在应用层进行验证：

**消息创建时**：
```rust
// 在 MessageValidator 中验证
if !message.is_ai_generated {
    // 验证 sender_id 是有效的用户 ID
    validate_user_exists(message.sender_id).await?;
} else {
    // 验证 sender_id 是有效的 AI Agent ID
    validate_agent_exists(message.sender_id).await?;
}
```

**消息查询时**：
```rust
// 根据 is_ai_generated 标志决定如何解析 sender_id
if message.is_ai_generated {
    let agent = get_agent(message.sender_id).await?;
    sender_name = agent.name;
} else {
    let user = get_user(message.sender_id).await?;
    sender_name = user.username;
}
```

## 数据完整性保证

虽然移除了外键约束，但我们通过以下方式保证数据完整性：

1. **应用层验证**：
   - 消息创建前验证 sender_id 的有效性
   - 根据 `is_ai_generated` 标志验证对应的表

2. **索引支持**：
   - `idx_messages_ai_generated`：快速查询 AI 消息
   - `idx_messages_sender_time`：按发送者查询消息历史

3. **业务逻辑约束**：
   - AI Agent 只能在所属群组发送消息
   - 用户只能发送自己的消息
   - 权限检查在消息路由层进行

4. **软删除**：
   - 删除 User 或 AI Agent 时，不删除历史消息
   - 保留消息记录用于审计和历史查看

## 未来改进

如果需要更严格的数据完整性，可以考虑：

1. **使用触发器**：
   ```sql
   CREATE OR REPLACE FUNCTION validate_message_sender()
   RETURNS TRIGGER AS $$
   BEGIN
       IF NEW.is_ai_generated THEN
           IF NOT EXISTS (SELECT 1 FROM ai_agents WHERE id = NEW.sender_id) THEN
               RAISE EXCEPTION 'Invalid AI Agent ID';
           END IF;
       ELSE
           IF NOT EXISTS (SELECT 1 FROM users WHERE id = NEW.sender_id) THEN
               RAISE EXCEPTION 'Invalid User ID';
           END IF;
       END IF;
       RETURN NEW;
   END;
   $$ LANGUAGE plpgsql;

   CREATE TRIGGER check_message_sender
   BEFORE INSERT OR UPDATE ON messages
   FOR EACH ROW EXECUTE FUNCTION validate_message_sender();
   ```

2. **使用视图**：
   ```sql
   CREATE VIEW messages_with_sender AS
   SELECT 
       m.*,
       CASE 
           WHEN m.is_ai_generated THEN a.name
           ELSE u.username
       END AS sender_name
   FROM messages m
   LEFT JOIN users u ON m.sender_id = u.id AND NOT m.is_ai_generated
   LEFT JOIN ai_agents a ON m.sender_id = a.id AND m.is_ai_generated;
   ```
